Mac 侧日常维护 3 件事

  1. 开机自动跑：注册 launchd（com.cores3os.bridge）后，下次登录生效；这次想手动开就双击 启动桥接.command。
  2. 改 Wi-Fi：不用重新烧固件。串口发 wifi YOUR_SSID YOUR_PASSWORD，设备会存进闪存并重启；reset 可恢复默认。
  3. 登录过期：CLI 的令牌约 3 天到期，到期后双击 登录.command 走一次交互登录即可。
桥接服务只做一件事：收 HTTP 请求 → 起一个 CLI 子进程 → 把结果写回 outbox 供设备轮询。它不碰你的界面、不需要辅助功能权限。

反向：让 WorkBuddy 主动找设备 MCP

  1. 已写好 MCP Server：~/.workbuddy/m5-bridge/mcp_cores3.py（零依赖，stdio）。
  2. 已登记进 ~/.workbuddy/mcp.json，名字 m5-cores3。
  3. 还需你做一步：重启 WorkBuddy，到连接器管理页对新出现的 m5-cores3 点「信任」。
工具效果
cores3_display在 CoreS3 屏幕上显示一段文字（中文可）
cores3_led控制 Bottom3 两侧 10 颗 RGB 灯
cores3_status查设备在线状态、电量

方向说明：MCP 只能由 WorkBuddy 主动发起，所以「设备 → 派活」走 HTTP 桥接、「WorkBuddy → 设备」走 MCP，两条路是分开的、各自都通了。

Back then the CoreS3 joined Wi-Fi and polled an HTTP bridge on the Mac, so you had to configure an SSID/password, watch the IP address and install a launchd job. The current firmware (v0.7.x) is pure BLE: no Wi-Fi, no IP, just mac-bridge/MusicBridge.app running on the Mac. Kept here only to show how the design evolved — for actual use see the cheat sheet and the README.

Check this table first when something breaks troubleshooting

SymptomMost likely causeWhat to do
No IP on the top line of the screen Wi-Fi not joined (wrong password, or a 5 GHz-only network) Send status over serial and check whether wifi= is 0 or 1; change networks with wifi NAME PASSWORD
Stuck on “running” after sending, then times out The bridge service isn't running on the Mac; or the CLI login expired (~3 days) Double-click ~/.workbuddy/m5-bridge/启动桥接.command; if that fails, double-click 登录.command and log in again
Typing on the keyboard does nothing on screen The Keyboard3 isn't seated properly, or I2C didn't initialise Send status and look at kb=; if it's 0, unplug the panel, reseat it and press the CoreS3 reset button
Both side LED strips are solid white and static The SELECTION switch on the Bottom3 board is in the wrong position Move it to the side marked Core2 / CoreS3 (the lower position); normal is a flowing pale-blue effect
The two blue keyboard LEDs never light The firmware defaults to led_mode=0, so they are simply off Not a fault. They light only when you press aA/sym/Fn/alt, and they blink once at power-on
Edited config.h, reflashed, behaviour unchanged Arduino reused a stale build cache Delete ~/Library/Caches/arduino/sketches/<HASH> before compiling; confirm with strings *.bin | grep <new string>

Mac-side housekeeping 3 things

  1. Runs at login: once the launchd job (com.cores3os.bridge) is registered it starts at the next login; to start it right now, double-click 启动桥接.command.
  2. Changing Wi-Fi: no need to reflash. Send wifi YOUR_SSID YOUR_PASSWORD over serial — the device stores it in flash and reboots; reset restores the default.
  3. Login expiring: the CLI token lasts about 3 days. When it expires, double-click 登录.command and go through the interactive login once.
The bridge does exactly one thing: receive an HTTP request → spawn a CLI subprocess → write the result back to an outbox the device polls. It never touches your UI and needs no accessibility permission.

The reverse direction: let WorkBuddy reach the device MCP

  1. An MCP server is already written: ~/.workbuddy/m5-bridge/mcp_cores3.py (zero dependencies, stdio).
  2. It is registered in ~/.workbuddy/mcp.json under the name m5-cores3.
  3. One step left for you: restart WorkBuddy, open the connector management page and click “Trust” on the newly appeared m5-cores3.
ToolEffect

cores3_ledControl the 10 RGB LEDs on both sides of Bottom3

Direction note: MCP can only be initiated by WorkBuddy, so “device → dispatch a task” goes over the HTTP bridge while “WorkBuddy → device” goes over MCP. The two paths are separate and both work.
