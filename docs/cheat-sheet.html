视觉主题 v0.2.0

从浅色卡片风整体换成 深底 + 霓虹 + 点阵字。核心是两套原生点阵字体： ASCII 用 M5GFX 内置的 Font8x8C64（C64 8×8 点阵，行优先，覆盖全 ASCII 含小写）， 中文用 efontCN_16（16×16 点阵）。两者都是位图，放大只会变成更大的方块、不会糊， 这正是像素风想要的。

面板底0x0B1017卡片 / 大按钮底
主文字0xB8C7D6冷白，次级用 C_DIM

双语（简中 / 英文）v0.3.0

界面文字全部走 S(StrID) 取串，不要写死字符串。切换后写进 NVS，掉电不丢。

怎么切说明
设置 → 语言 行点右侧方块在 简中 / ENGLISH 之间切，立即重绘全界面（含导航条应用名）
串口 lang cn / lang en不带参数直接 lang = 反向切换
英文模式长什么样纯 ASCII + 8×8 点阵，更像真正的终端：日期 2026-09-20、星期 SUN、按钮 REC / SEND / CANCEL
英文串必须纯 ASCII。8×8 点阵里没有汉字，混进 ·、→ 这类非 ASCII 符号（UTF-8 里 >= 0x80） 会被 hasCJK() 判成中文、改用 16×16 点阵，排版行高就变了。所以英文串里统一用 / 代替 ·。
两张表靠 static_assert 对账：数组故意不写长度，跟 StrID 枚举数量不一致时直接编译不过， 不会出现「中文对英文串味」这种难查的 bug。

手势：左缘右滑返回 v0.1.3

CoreS3 是电容触摸屏，M5Unified 的 Touch_Class 底层自带 flick / drag / hold 状态机（判定「手指动了多少」），但没有「这个动作是什么意思」这一层—— 手势语义由外壳自己写。

判定条件（三条同时满足）取值
起手点在屏幕左缘base_x <= GEST_EDGE(40)
向右位移够远distanceX() >= GEST_MIN_DX(44)
上下没跑偏|distanceY()| <= GEST_MAX_DY(44)（避免竖向拖被误判）
移动阈值（交给 M5Unified）setFlickThresh(16)：小于它的抖动仍算点击
点击是「抬手才派发」，不是「按下即派发」。 否则按下那一帧就被应用消费掉了，手势根本没有介入的机会。改成抬手派发后， 按下之后可以靠滑动取消这次点击——和手机上的行为一致。
「返回上一级」统一走 goBack()：先问应用 onBack()， 应用返回 false 或没实现（nullptr）才回桌面。v0.4.0 起控制器只剩一页 （预设二级页已删），onBack() 空着，留给将来带二级页的应用。

串口命令 调试

  • status — 当前应用/蓝牙/键盘/电量/亮度/休眠
  • apps — 列出所有应用编号与名字（跟随当前语言）
  • lang cn / lang en — 切语言，写入 NVS；单输 lang = 反向切
  • launch N — 直接启动第 N 个应用
  • home — 回桌面
  • back — 返回上一级（等价于左滑手势）
  • unpair — 重启蓝牙广播（重新配对用）
  • bright 0-255 — 改亮度
  • sleep 秒 — 改息屏时间，0 = 常亮
  • focus 0-7 — 新建对话后的聚焦方式（0=OFF 默认，1-3=S-TAB1-3，4-6=TAB1-3，7=WAKE 实测会带走焦点，别用）
  • fdelay <ms> — 聚焦前先等多久（200-5000，默认 1800）
  • rec 0|1 — 录音方式（0=WorkBuddy 内置语音 Cmd+D，1=macOS 听写）
  • clear 0|1|2 — 取消键档位（0=ESC，1=WIPE，2=ESC+WIPE 默认）
  • act rec|send|cancel|new|prev|next — 直接跑固件真实按键路径（自测用，别手动拼键）
  • key <0-255> — 模拟 Keyboard3 物理按键，走同一条 onKey 派发路径（key 127 = 按 del，key 32 = 空格，key 13 = 回车）。验键位映射用
  • music — 打印歌曲元数据与封面收发进度（art=已收/总长 (ready)）
  • time [YYYY-MM-DD HH:MM:SS] — RTC 对时（v0.5.1）。不带参数 = 打印当前 RTC；带参数 = 写入，星期自己算
  • note — 打印记事本状态（fs/sub/sending/queued/sent/len/draws）。 draws 是重绘次数：静置时它不该涨，涨了说明又退回按节拍重绘了
  • note push <文本> — 走真实发送路径推一条速记（不碰屏幕就能验链路，v0.6.0）
  • note type <文本> — 逐字符喂给 appNoteKey() 再补 ALT+S，等于「模拟真人在 Keyboard3 上打完这行并按发送」。验按键映射（含 0x08/0x7F 退格、0x0D 换行）用这条
  • fs — flash 文件系统体检：分区信息（label=lfs）/ 挂载 / 写测试 / 列根目录；找不到分区时会把整张 data 分区表打出来（v0.6.0）
  • fs2 — 更底层：裸分区 erase+write+read 读回校验，并对比 open("/x") 与 open("/littlefs/x")
  • reboot — 硬重启（烧录后必发一次，fw.sh 已自动带上）

怎么加一个新应用 扩展

  • 1. 新建 app_xxx.ino，实现 5 个入口函数（onBack 可选）
  • 2. 在 shell.h 里声明这些函数
  • 3. 在 i18n.h 的 StrID 加应用名，并在 i18n.ino 两张表里各补一条
  • 4. 在 cores3_shell.ino 的 g_apps[] 加一行：nameId + 霓虹主色 + 8×8 图标
  • 5. 图标是 8 字节位图，0x80 是最左像素（跟 C64 字体数据同格式）
// app_xxx.ino
#include "shell.h"
static const uint8_t ICON[8] = {0x18,0x3C,0x7E,0x5A,0x5A,0x7E,0x3C,0x18};
void appXxxStart() { clearCanvas(); drawTitle(40, S(S_XXX_TITLE), C_CYAN); }
void appXxxLoop()  {
  static uint32_t last = 0;
  if (!uiTick(last)) return;    // 统一 1Hz 节拍
  // 再做内容脏检查：值没变就直接 return，屏幕不闪
}
void appXxxTouch(int16_t x, int16_t y) { /* y>=CANVAS_Y(36) */ }
void appXxxKey(uint8_t raw) { /* 0x0D 0x1B 0x20 ... */ }
void appXxxStop()  { }
// 可选：返回 true = 左滑/Esc 先在应用内部返回（二级页）
bool appXxxBack()  { return false; }
坑 1：所有 .ino 会被合并成一个编译单元， static const 常量和 static 函数不能跨文件重名。 常量加应用前缀（PMO_X、SEN_X），同名辅助函数改名（infoRow / senLine）。
坑 2：导航条占 y < CANVAS_Y(36)，应用内容从 y >= 40 开始排， 底部别超过 226（240 高屏，中文一行 16）。
坑 3：ASCII 数值区只能放 ASCII——用 8×8 点阵字体画中文会出空白， 中文一律走 setCnFont()（如电量行写 93% BAT 而不是 93% 放电中）。
坑 4（双语）：界面文字一律 S(StrID)，别写死；成组的串（星期、休眠档） 在枚举里必须连续，代码靠「基址 + 下标」取。垂直居中用 textHeight(s) 算， 别写死 16——英文模式下是 8，写死会整体偏上。

已知约束 重要

  • 灯带必须保持关闭（ENABLE_BOTTOM3_LED 0）：Adafruit NeoPixel 在 ESP32-S3 上有已知 bug（官方 issue #429），show() 走 RMT，无线电繁忙时触发断言并无限重启。开 BLE 后必现。
  • 默认分区只有 3MB APP 且无 OTA 槽：现在是「一个固件装所有应用」，加应用要重新编译烧录。想做成运行时安装/卸载，得先写自定义分区表（启动器 1.5MB + 4×2MB 应用槽）。
  • 改代码后必须 compile --clean：arduino-cli 的缓存不会因为 config.h 变化而失效，容易烧进旧固件。
  • 烧录前设备要接 USB 并开机：串口是 /dev/cu.usbmodem*，但编号每次插拔/换 USB 口都会变 （实测见过 101 和 2101）——一律自动探测，别硬编码（fw.sh / ser.py 已这么做）。找不到就单击电源键开机再试。
  • RTC 没有后备电池：掉电或重烧后时间归零，而设备本身没有任何对时来源（没 Wi-Fi、BLE 也不给时间）。 用串口 time YYYY-MM-DD HH:MM:SS 对时，或直接跑 tools/rtc.sh （fw.sh 每次烧完会顺手同步一次）。星期由日期自己算（Sakamoto 算法），不用传。
  • Cmd+[ / Cmd+] / Cmd+N / Cmd+D 都是 WorkBuddy 原生快捷键（应用包内快捷键定义表： prev-task=Meta+[、next-task=Meta+]、new-conversation=Meta+N、toggle-voice-recording=Meta+D）， 不需要在 Mac 侧做任何映射。
  • 「焦点在不在输入框」是整套控制器的命门（v0.4.3 才查清，之前的结论是错的）。 Cmd+D 只绕开了「录音」这一步，绕不开「发送」和「取消」。源码依据： ① 录音 toggle-voice-recording 的处理是 window.addEventListener("keydown", …)， 挂在 window 上，与焦点无关 —— 所以新建对话后照样能录音、文字也照样进输入框； ② 但应用包的 APP_SHORTCUT_IDS（window 级快捷键白名单）里没有 send-message， 它的处理在输入框内部的 React onKeyDown（handleInsertNewline 匹配到 Enter 才 return true 触发发送）。 所以 Enter 只有在焦点位于输入框内时才有效；Cmd+A 同理 —— 焦点在输入框是全选输入内容， 焦点在 body 就是 Chromium 的 select-all，表现为「全选了整个页面的文字且不删除」。 这解释了为什么「已有的对话一切正常、新建的却不行」：跟新建无关，只跟焦点有关 —— 已有对话之所以正常，是因为你之前用鼠标点过输入框，焦点一直在那儿；new-conversation 只跳转、不聚焦。
  • v0.4.3~v0.4.5 的 Tab 遍历、v0.4.6 的 WAKE 档，OCR 实测全部失败 —— v0.4.8 默认改回「不补按」。
    Tab 遍历失败的原因：① Electron 里 Tab 落点跟 DOM 顺序强相关，正向先撞侧边栏一堆按钮、反向也未必落在输入框； ② 新对话的输入框什么时候挂载不确定（等待已从 800ms 放宽到 1800ms 也没救回来）。
    WAKE 档（Cmd+D 双击）实测证伪，这个结论很重要：原以为语音结果回调 text => { appendInputText(text); focusInput(); } 会在录音结束时把焦点送回输入框， 但无声时 WorkBuddy 走的是「未检测到语音内容，请重试」这条分支，焦点不但没回来，反而被语音面板带走。 OCR 对照铁证：输入框里打 QZDD → wake → wipe，结果只剩 QZD（全选失效、 Backspace 退化成删一个字符）；而 esc → wipe 则清空到 placeholder。

  • v0.4.4：取消键对齐 VibeKey，改发 ESC（原来是自己设计的 Cmd+A+Delete，错了）。 WorkBuddy 快捷键定义表里的完整答案：stop-generation = Escape、 send-message = Enter、newline = Shift+Enter、new-conversation = Meta+N、 prev/next-task = Meta+[ / Meta+]、toggle-voice-recording = Meta+D。 → Esc 在 WorkBuddy 里的语义是「停止生成」，不是「清空输入框」： 任务正在跑时按它 = 中断；想清空草稿文字得用 WIPE 档（串口 clear 1，= Cmd+A + Delete，需焦点在输入框）。 为什么放弃 Cmd+A+Delete 作默认：焦点不在输入框时它会退化成 Chromium 的 select-all， 表现就是「全选整个页面的文字且不删除」——正是 v0.4.2/v0.4.3 实测到的症状。
  • v0.4.5：取消键 = ESC + 清空草稿，两连击（默认档）。 顺序是 Esc → 等 220ms → Cmd+A → 等 80ms → Backspace。 Esc 负责「停止生成」（不依赖焦点，稳），Cmd+A+Backspace 负责「清空草稿」（需要焦点在输入框）。
    v0.4.8 修掉了「已有对话取消也失效」这个回归：v0.4.6/v0.4.7 里 actClear() 会跟着 focus 设置跑一次唤醒（当时默认 WAKE = Cmd+D 双击），语音面板把焦点带走 → Cmd+A 全选失效、Backspace 只删一个字符，表现就是「取消清不掉草稿」。 修法是取消时一个多余按键都不发（CANCEL_WAKE_FOCUS = 0）—— 已有对话里焦点本来就在输入框（能打字就是证据），唤醒纯属把焦点弄丢。 想恢复唤醒就改 config.h 里的 CANCEL_WAKE_FOCUS 为 1。
    v0.4.6 修了一个隐藏 bug：删除键从 KEY_DELETE(0x4C) 改成 KEY_BACKSPACE(0x2A)。 HID 的 Delete 在 Mac 上等于 Fn+Delete「向前删」，Electron/Chromium 里选区存在时经常不生效； Backspace 才是 Mac 键盘上那颗 delete 键真正发的码 —— 这一条可能就是「全选了但删不掉」的元凶。 合成一档的理由：单独 Esc 说错了重录时旧草稿还在，文字会追加；单独 WIPE 又中断不了正在跑的任务。 最坏情况（焦点在 body）只是「清不掉草稿」而不会误删任何东西，可以接受。 串口 clear 0 退回纯 ESC、clear 1 只要清空。

v0.5.1 修的两个问题

  • 封面一直不显示（NO ART） —— 缓冲上限定小了。QQ 音乐的封面压成 160×160 JPEG 后是 14777 字节，而 MUSIC_ART_MAX 写的是 12288：首包里的 total 一进来就被判 「超限」丢弃，续包却照收不误 → 缓冲塞满、artTotal 还是 0、 artReady 永远起不来。串口的判据很直观：art=12288/0。
    修法：上限提到 32768（PSRAM 有 8MB），并给续包加了门禁 ——没收到合法首包就丢弃、已收齐还来的重复包也丢弃，不会再出现「半张图被当成整张」。 修完串口是 art=14777/14777 (ready)，日志 [music] 封面解码成功并上屏。
  • 整屏每秒重画一次 —— 封面 JPEG 每秒重新解码，屏幕肉眼可见地闪，而真正要动的只有进度条。
    现在分三档：① 曲目/播放状态/蓝牙变了、或新封面收齐 → 整屏重画（dirty 由 GATT 回调置位）； ② 播放时间往前走了一秒 → 只重画「时间 + 进度条」那一条（clearArea 会补回网格底纹，看不出接缝）； ③ 暂停中或还没到下一秒 → 一个像素都不动。
    关键细节：Mac 端每 2 秒推一次 meta（里面带进度），所以 musParseMeta 必须区分「曲目/状态变了」和「只是进度刷新」， 否则 dirty 每 2 秒置一次，等于又退回整屏闪。

链路与协议

  • 方向跟音乐模块相反：音乐是 Mac 写、设备读；记事本是设备 notify、Mac 订阅。 同一个 NimBLEServer 上再挂一个 NOTE_SVC（OUT 用 NOTIFY、ACK 用 WRITE）。
  • 分包协议跟封面那条对称：首包 [0]=0xA5 + [1..2]=总长(u16 LE)，续包 [0]=0x5A； Mac 端收够总长就拼起来落盘，然后往 ACK 写 0x01。
  • Mac 端不订阅就什么都收不到 —— setNotifyValue(true, for:) 是必须的， 忘了的话 Bridge 日志里永远看不到 [note] →。
  • 没订阅 / 发送失败 / 等回执超时（5 秒） → 内容落 flash 队列（/nq00000001.txt， 编号存 NVS 单调自增），等下次连上自动补发，补发成功才删文件。草稿同样落盘，掉电不丢。 用的是分区表里那块 9.9MB 的分区，跟挂不上的 exFAT TF 卡没关系。
  • ★ 存储用 LittleFS，不用 FFat：FFat 在这块板上能挂载（total=9996KB）但 任何 FILE_WRITE 都失败。为此分区表换成了 partitions.csv（sketch 目录里那份）， 把那块 data 分区的 subtype 从 fat 改成 0x83（littlefs）。
  • ★ open() 的路径不能带挂载点前缀：挂载点给 begin() 用（/littlefs）， 而 open() 要传 fs 内部路径 "/nq00000001.txt"；写成 "/littlefs/nq00000001.txt" 必然打不开 —— FFat 当初"写不了"其实也是这一个坑， 不是文件系统坏了（裸分区擦写实测成功）。排查跑 fs2。
  • 补发和草稿存盘都做了节流（2 秒一次）：队列要扫一遍目录，每帧都扫会把 flash 读爆。 草稿是「停手 2 秒才写一次」，不是每敲一个键就写。
  • ★ 离线笔记带的是书写时间，不是送达时间（v0.6.2）：内容离开编辑区那一刻， 设备把当时的 RTC 烙进正文前面，格式固定 19 字节 [YYYY-MM-DD HH:MM] ； 队列文件里也带着它，所以隔多久补发都不丢。Bridge 认这个前缀就拿它当条目时间和 ## 日期 小标题 —— 昨天写的会归回昨天，并按日期顺序插进正确位置。 没有前缀（老固件 / RTC 归零）才退回 Mac 当前时间。
  • ★ 连上 Bridge 会自动对时（v0.6.2）：CoreS3 的 RTC（BM8563）没有后备电池， 掉电 / 重烧会归零，不对时就没法烙书写时间。所以 Bridge 每次发现 ACK 特征就往里写 7 字节 0x02 + 年-2000 + 月 + 日 + 时 + 分 + 秒（复用 ACK 通道，不新增特征）。 传年月日而不是 epoch —— 设备端没设 TZ，走 epoch 要多处理一次时区。
  • 入队失败时不再清空编辑区（v0.6.2）：原来队列满（32 条）或 fs 不可用时也返回 「成功」，上层就把编辑区清了 —— 那条内容真没了。现在返回失败，内容留在屏幕上。
  • ★ 界面是静态的，不每秒重绘（v0.6.1）：原来挂了 1Hz 节拍，等于每秒整屏重画一次， 肉眼看就是一闪一闪。现在只有「内容真变了」才重画 —— 打字 / 退格 / 清空 / 移光标、 发送结果、以及 BLE 连接与订阅状态、队列数变化时各重画一次，其余时间一个像素都不动。 串口 note 里的 draws= 就是重绘次数：静置时它不涨。
  • 串口：note 看状态；note push Hello 直接推一条（走真实发送路径）； note type Hello 模拟按键打完再按发送（连 appNoteKey() 一起验）。
  • 重刷固件不会丢待发内容：队列文件在独立 data 分区里，fw.sh 只写 app 分区。 实测重启后 Bridge 一订阅就自动补发，queued 归 0、last=已送达。

  • 先试过加第 7 个应用，但 3 列排不下：第 7 个会落到 y=218、底边 296， 超出 240 的屏幕；改成 4 列 × 2 行后 tile 只剩 71px 宽，英文应用名被迫缩短成 CTRL / POMO / SYS / SET。

  • 时间并没有丢 —— 状态栏一直在显示 HH:MM，RTC 对时命令 time 也照旧。 时钟源码保留为 app_clock.ino.bak（后缀不是 .ino 就不参与编译），想换回来改个名即可。

Known constraints important

  • The LED strip must stay off (ENABLE_BOTTOM3_LED 0): Adafruit NeoPixel has a known bug on the ESP32-S3 (upstream issue #429) — show() uses RMT and trips an assert when the radio is busy, causing endless reboots. Guaranteed once BLE is on.
  • The default partition gives 3MB APP and no OTA slot: one firmware holds every app, so adding an app means recompiling and reflashing. Runtime install/uninstall would need a custom table first (launcher 1.5MB + 4×2MB app slots).
  • Always compile --clean after editing code: arduino-cli's cache isn't invalidated by changes to config.h, so stale firmware gets flashed.
  • The device must be plugged in and powered on before flashing: the serial port is /dev/cu.usbmodem*, but the number changes on every replug or port change (101 and 2101 both seen) — always auto-detect, never hard-code (fw.sh / ser.py already do). If it isn't found, tap the power button and retry.
  • The RTC has no backup battery: time resets on power loss or reflash, and the device has no way to obtain time (no Wi-Fi, BLE carries none). Sync it with serial time YYYY-MM-DD HH:MM:SS or just run tools/rtc.sh (fw.sh calls it after every flash). The weekday is computed from the date (Sakamoto's algorithm), no need to pass it.
  • Cmd+[ / Cmd+] / Cmd+N / Cmd+D are all native WorkBuddy shortcuts (from the app bundle's shortcut table: prev-task=Meta+[, next-task=Meta+], new-conversation=Meta+N, toggle-voice-recording=Meta+D), so nothing needs mapping on the Mac side.
  • “Is focus inside the input box?” is the crux of the whole controller (only understood properly in v0.4.3 — earlier conclusions were wrong). Cmd+D bypasses the recording step, but not sending or cancelling. Evidence in the source: ① recording is handled by a window.addEventListener("keydown", …), bound to window and therefore focus-independent — so you can still record after creating a new conversation and the text still lands in the box; ② but the bundle's APP_SHORTCUT_IDS (window-level shortcut allow-list) does not include send-message — it's handled by a React onKeyDown inside the input box (handleInsertNewline returns true on Enter to trigger a send). So Enter only works when focus is inside the input box; same for Cmd+A — inside the box it selects the input text, on body it's Chromium's select-all, which looks like “the whole page got selected and nothing was deleted”. That's why “existing conversations work, new ones don't”: it's not about new, it's about focus — existing ones work because you clicked the box earlier and focus stayed there; new-conversation only navigates, it doesn't focus.
  • Tab walking (v0.4.3–v0.4.5) and the WAKE option (v0.4.6) all failed in on-screen tests — v0.4.8 went back to “press nothing” by default.
    Why Tab walking fails: ① in Electron the Tab landing order follows DOM order, so forward hits a pile of sidebar buttons and backward doesn't necessarily land on the input box; ② you can't know when the new conversation's input box mounts (widening the wait from 800ms to 1800ms didn't save it).
    The WAKE option (double Cmd+D) was disproven, and that matters: the assumption was that the voice result callback text => { appendInputText(text); focusInput(); } returns focus to the box when recording ends, but when there's no audio WorkBuddy takes the “no speech detected, please retry” branch, and focus is taken away by the voice panel instead. OCR evidence: type QZDD in the box → wake → wipe leaves QZD (select-all failed, Backspace degraded to deleting one char); esc → wipe clears all the way back to the placeholder.
    → Hence the default is FOCUS_OFF again: better to press nothing than to send keys that lose focus. The option cycles in Settings → focus after new (serial focus 0-7, NVS key fmode); WAKE is kept but no longer default. New conversations still aren't solved — for now, tap the input box once after creating one.
  • v0.4.4: the cancel key now sends ESC, matching VibeKey (the earlier Cmd+A+Delete was a wrong guess). The full answer from WorkBuddy's shortcut table: stop-generation = Escape, send-message = Enter, newline = Shift+Enter, new-conversation = Meta+N, prev/next-task = Meta+[ / Meta+], toggle-voice-recording = Meta+D. → In WorkBuddy, Esc means “stop generating”, not “clear the input box”: pressing it while a task runs interrupts it; to clear the draft text you need the WIPE mode (serial clear 1, = Cmd+A + Delete, requires focus in the box). Why Cmd+A+Delete isn't the default: without focus in the box it degrades into Chromium's select-all — “the whole page gets selected and nothing is deleted”, exactly what v0.4.2/v0.4.3 measured.
  • v0.4.5: cancel = ESC + clear draft, as a two-step combo (default). Order: Esc → wait 220ms → Cmd+A → wait 80ms → Backspace. Esc handles “stop generating” (focus-independent, reliable); Cmd+A+Backspace clears the draft (needs focus in the box).
    v0.4.8 fixed the regression where cancelling broke in existing conversations too: in v0.4.6/v0.4.7 actClear() performed a wake according to the focus setting (then default WAKE = double Cmd+D), and the voice panel took focus away → select-all failed, Backspace deleted one char, i.e. “cancel doesn't clear the draft”. The fix is to send no extra key at all when cancelling (CANCEL_WAKE_FOCUS = 0) — in an existing conversation focus is already in the box (being able to type proves it), so waking only loses it. Set CANCEL_WAKE_FOCUS to 1 in config.h to restore the wake.
    v0.4.6 also fixed a hidden bug: the delete key changed from KEY_DELETE(0x4C) to KEY_BACKSPACE(0x2A). HID Delete on macOS means Fn+Delete (forward delete) and often does nothing when a selection exists in Electron/Chromium; Backspace is what the physical delete key on a Mac keyboard actually sends — quite possibly the culprit behind “selected but won't delete”. Why the combo: ESC alone leaves the old draft in place when you re-record after misspeaking (text gets appended); WIPE alone can't interrupt a running task. Worst case (focus on body) is only “draft not cleared” and never deletes anything by mistake, which is acceptable. Serial clear 0 goes back to plain ESC, clear 1 only clears.

The Mac-side Music Bridge

mac-bridge/MusicBridge.app (source Bridge.swift): every 2 seconds it runs media-control get (MediaRemote) and writes title/artist/album/position into the META characteristic, then pushes the artwork as a 160×160 JPEG in chunks into ART. On first run you must allow it in System Settings → Privacy & Security → Bluetooth, otherwise CoreBluetooth never calls back (the log stops at [bridge] scanning…).

  • The bundle must be signed explicitly: codesign -s - -f --deep MusicBridge.app. Unsigned, the signature says Info.plist=not bound, TCC can't read NSBluetoothAlwaysUsageDescription → immediate SIGABRT (crash report namespace=TCC). After signing you should see Info.plist entries=7.
  • NimBLE stops advertising as soon as it connects → the Mac can't find it. So the main loop calls NimBLEDevice::startAdvertising() every 15 seconds (idempotent while connected — it won't drop the existing connection).
  • QQ Music 11.9.1 is confirmed working: its binary contains -[QQMusicMainPlayerController setupMPRemoteCommand], so MPRemoteCommandCenter is registered and both channels (media keys and MediaRemote metadata) are open. But it ships no sdef and no NSAppleScriptEnabled → native AppleScript is unavailable, so “like / play mode” can only be driven through System Events by clicking the “playback control” menu (locate it by name, not by index).
  • Apple Music hijacks the media keys (MediaRemote gives it top priority) — quit it completely with ⌘Q before use; closing the window isn't enough.
  • Serial: music prints the track state received so far and the artwork progress.

Two problems fixed in v0.5.1

  • Artwork never showed (NO ART) — the buffer cap was too small. QQ Music's artwork is 14777 bytes once downscaled to 160×160 JPEG, while MUSIC_ART_MAX was 12288: the total in the first chunk was rejected as “over limit” and dropped, while following chunks were still accepted → the buffer filled up, artTotal stayed 0 and artReady never rose. The serial tell is clear: art=12288/0.
    Fix: raise the cap to 32768 (there's 8MB of PSRAM) and gate the continuation chunks — drop them when no valid first chunk arrived, and drop duplicates once the image is complete, so a half image can never be mistaken for a whole one. Afterwards the serial reads art=14777/14777 (ready) and the log says [music] artwork decoded and drawn.
  • The whole screen repainted once per second — the artwork JPEG was decoded again every second (visible flicker) even though only the progress bar actually moved.
    Three tiers now: ① track/play state/BLE changed, or a new artwork arrived complete → full repaint (dirty is set by the GATT callback); ② playback time advanced by a second → repaint only the “time + progress bar” strip (clearArea restores the grid texture, so the seam is invisible); ③ paused, or the next second hasn't arrived → not a single pixel.
    Key detail: the Mac pushes metadata every 2 seconds (including position), so musParseMeta must distinguish “track/state changed” from “just a position refresh” — otherwise dirty gets set every 2 seconds and you're back to a flickering screen.

Chain and protocol

  • The direction is the opposite of the music module: music is Mac-writes / device-reads, notes are device-notifies / Mac-subscribes. A second service NOTE_SVC hangs off the same NimBLEServer (OUT = NOTIFY, ACK = WRITE).
  • The chunking protocol mirrors the artwork one: first chunk [0]=0xA5 + [1..2]=total length (u16 LE), continuation chunks [0]=0x5A; the Mac assembles once it has the full length, writes it out, then writes 0x01 to ACK.
  • If the Mac doesn't subscribe you receive nothing — setNotifyValue(true, for:) is mandatory; forget it and [note] → never appears in the Bridge log.
  • Not subscribed / send failed / ack timed out (5s) → the content goes to a flash queue (/nq00000001.txt, with a monotonic counter in NVS) and is replayed automatically on the next connection; the file is deleted only after a successful replay. Drafts are persisted too, so nothing is lost on power loss. This uses the 9.9MB partition from the partition table — unrelated to the exFAT TF card that won't mount.
  • ★ Storage is LittleFS, not FFat: FFat mounts on this board (total=9996KB) but every FILE_WRITE fails. Hence the custom partitions.csv in the sketch directory, which changes that data partition's subtype from fat to 0x83 (littlefs).
  • ★ open() paths must not carry the mount prefix: the mount point is for begin() (/littlefs) while open() takes the filesystem-internal path "/nq00000001.txt"; "/littlefs/nq00000001.txt" always fails — this was also the real reason FFat “couldn't write”, not a broken filesystem (raw partition erase/write tests succeed). Run fs2 to diagnose.
  • Both replay and draft saving are throttled (once per 2 seconds): replaying scans a directory, and doing that every frame would hammer the flash. The draft is written 2 seconds after you stop typing, not on every keystroke.
  • ★ Offline notes carry their writing time, not the delivery time (v0.6.2): the moment the text leaves the editor, the device stamps the RTC into the front of the body as a fixed 19-byte [YYYY-MM-DD HH:MM] prefix; the queue file carries it too, so however long the replay takes, the time isn't lost. The Bridge recognises the prefix and uses it as the entry time and as the ## date sub-heading — something written yesterday is filed under yesterday and inserted in the right date order. Only when the prefix is missing (old firmware / RTC at zero) does it fall back to the Mac's current time.
  • ★ Connecting to the Bridge syncs the clock automatically (v0.6.2): the CoreS3's RTC (BM8563) has no backup battery; it resets on power loss or reflash, and without a correct time the writing-time stamp is meaningless. So every time the Bridge discovers the ACK characteristic it writes 7 bytes 0x02 + year-2000 + month + day + hour + min + sec into it (reusing the ACK channel, no new characteristic). Year/month/day rather than an epoch — the device sets no TZ, so an epoch would need a timezone conversion too.
  • A failed enqueue no longer clears the editor (v0.6.2): previously a full queue (32 items) or an unavailable filesystem still returned “success” and the layer above cleared the editor — the content was genuinely gone. Now it returns failure and the text stays on screen.
  • ★ The screen is static now, no per-second repaint (v0.6.1): it used to hang off a 1Hz tick, i.e. a full repaint every second, which you could see flicker. Now it only repaints when something actually changed — typing / backspace / clear / cursor move, the send result, and BLE connection & subscription state or queue count changes; the rest of the time not a pixel moves. draws= in the serial note output is the repaint counter: it must not increase while idle.
  • Serial: note shows the state; note push Hello pushes a note directly (through the real send path); note type Hello simulates typing and then pressing send (so appNoteKey() is exercised too).
  • Reflashing doesn't lose pending notes: the queue lives in a separate data partition and fw.sh only writes the app partition. Verified: after a reboot, as soon as the Bridge subscribes it replays, queued goes to 0 and last=delivered.

Why “replace Clock” instead of adding a 7th

  • Adding a 7th app was tried first, but 3 columns can't fit it: the 7th would land at y=218 with a bottom edge at 296, past the 240px screen. Switching to 4 columns × 2 rows shrank tiles to 71px wide and forced the English app names down to CTRL / POMO / SYS / SET.
  • So Notes replaced Clock and the count stayed at 6: the desktop went back to 3 columns × 2 rows (tiles 94×78) and full English names returned CONTROLLER / NOTES / POMODORO / SYSTEM / MUSIC / SETTINGS.
  • The clock wasn't really lost — the status bar always shows HH:MM and the time serial command still works. The clock source is kept as app_clock.ino.bak (a non-.ino suffix keeps it out of the build); rename it to bring it back.

Mac-side Bridge runs at login

In mac-bridge/. It does two things: push the Mac's now-playing track to the device screen, and subscribe to the device's notes and write them into a markdown file. It must stay running — while it isn't, notes on the device just queue up and wait.

Two traps when setting it up

  • ★ launchctl bootstrap always fails in a background shell: in processes with no GUI audit session (an AI tool's shell, an ssh session) it reports Bootstrap failed: 5: Input/output error regardless of plist content — even Apple's own plists fail the same way. Workaround: osacompile a tiny app that just runs the shell command and open it so it executes inside the GUI session. bridge.sh already contains that fallback, so don't type launchctl by hand — use the script.
  • Don't use open MusicBridge.app as the auto-start entry: open returns immediately, launchd thinks the process exited and restarts it forever. Put the absolute path .app/Contents/MacOS/MusicBridge in the plist.
  • Rebuilding means re-granting Bluetooth: ./build.sh re-signs, the cdhash changes, and TCC may ask again. Symptom: the log stops at [bridge] scanning… followed by ✗ 蓝牙未授权; go to System Settings → Privacy & Security → Bluetooth, tick it, then ./bridge.sh restart.
  • KeepAlive=true + ThrottleInterval=10: relaunched 10 seconds after a crash. Verified — after kill -9 it comes straight back with a new pid.
